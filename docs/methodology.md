# Методика

## Набор контрольных проб

Один сеанс наблюдения использует общие метки `run` и `target`. `target` объединяет контрольные точки одного проверяемого VPN-пути. `vantage` обозначает устройство или серверный процесс, `network` — фактически различимую сеть. Для каждой новой попытки задайте новый `attempt`. Пробы одного устройства в одной попытке используют ту же метку `attempt` для разных этапов. Метка `profile` обозначает одну сопоставимую конфигурацию туннеля, без реквизитов.

| Этап | Что измерять |
| --- | --- |
| `baseline` | Работает ли обычный HTTPS из клиентской сети при отключённом VPN |
| `ingress` | Доступен ли обычный сервис на входном узле, например HTTP/3 с проверкой TLS |
| `session` | Установлена ли свежая VPN-сессия |
| `tunnel` | Прошёл ли сквозной запрос в сессии с проверкой ожидаемого выходного IP |
| `egress` | Совпадает ли ожидаемый выход при независимой серверной проверке |
| `telemetry` | Пакеты, байты и качество измерения на интерфейсе |

`session` и `tunnel` — два свидетельства. Успешный HTTPS по уже открытой или прямой сессии может подтвердить IP, а свежую VPN-сессию проверяет отдельная запись. Снимайте контрольные пробы близко по времени. При сбое повторите попытку на том же устройстве с той же конфигурацией и проверьте другой маршрут доступа и серверный контроль. Прямую клиентскую пробу привязывайте к той же попытке, проведя её до подключения или сразу после отказа.

## Формат наблюдений

Одна строка JSONL содержит одну запись с `schema: 2`.

- `run`, `target`, `vantage`, `network`, `attempt`, `profile`, `method` и `reason` используют короткие метки строчными латинскими буквами, цифрами, дефисами и подчёркиваниями. Метка начинается с буквы. Активной записи нужен `attempt`, а этапам `session` и `tunnel` также нужен `profile`.
- `role` принимает `client` или `server`. `observed_at` содержит ISO 8601 с часовым поясом и приводится к UTC.
- `stage` — этап из таблицы. `outcome` — `pass`, `fail`, `unknown` или, для телеметрии, `observed`. `unknown` обозначает невозможность надёжно выполнить замер.
- `source` отличает ручной ввод (`manual`), HTTPS-пробу (`probe`), данные локального журнала (`journal`) и историю v1 (`legacy`).
- `egress_verified` требуется для положительного контроля `tunnel` или `egress`. Для телеметрии `window_start` задаёт начало окна, `observed_at` — его конец. `metrics` содержит неотрицательные целые значения.

Записи v1 читаются как `legacy`. Они видны в счётчиках истории, а неполные положительные результаты v1 не участвуют в новых выводах. Повторная запись или конвертация формата не восстанавливает отсутствующую информацию о сессии и происхождении.

## Интерпретация

По умолчанию `report` рассматривает последние 600 секунд от текущего времени. Для разбора прошлого инцидента укажите `--as-of` с часовым поясом. Записи за пределами окна и будущие метки считаются отдельно. Пара контрольных замеров должна укладываться в `--control-skew`, по умолчанию 120 секунд. Клиентские результаты всех этапов доступны в `client_checks`.

- `reachable_from_tested_networks` требует положительного `session` перед положительным `tunnel` с проверенным IP на той же точке, с теми же `attempt` и `profile`.
- `client_path_issue_suspected` требует двух попыток в разные моменты на одной точке, с одной конфигурацией, методом, источником и сетевым симптомом. У каждой должен быть собственный успешный прямой контроль и близкие по времени успешная сквозная проба в другой сети и серверные контроли входа и выхода. Ошибка сертификата, авторизации, DNS или неверный выход остаются отдельными причинами отказа.
- `client_failures_need_controls` означает, что для локализации клиентского отказа сопоставимых данных недостаточно. `egress_check_failed` и `server_checks_need_review` указывают на серверные пробы для проверки. Контрольный узел HTTPS тоже может отказать независимо от VPN.
- `attribution` остаётся `unestablished`. Для атрибуции фильтрации нужны воспроизводимое избирательное поведение и локализация потерь. [Пример исследования QUIC](https://petsymposium.org/foci/2026/foci-2026-0010.pdf)

Покрытие телеметрии оценивается внутри окна сравнения по каждому потоку с общей точкой наблюдения, сетью и методом. Отчёт отмечает точные дубли, конфликтующие счётчики для одного окна, перекрытия и непокрытое время. Непокрытое время включает ещё незаписанную часть текущего окна. Суммы пакетов в перекрывающихся окнах не складываются. Потери очереди и нечитабельные длины отмечают неполный счёт, а отсутствие показателя качества — неизвестное качество. Эти счётчики не измеряют потери пакетов на всём пути VPN.

## Адаптер Hysteria2

На вход подаётся доверенный локальный `journalctl -o json`. Импорт требует роли `server` и проверяет `_SYSTEMD_UNIT` по сопоставлению с `--tunnel-unit`, `--http3-unit` и `--telemetry-unit`. Для активной проверки нужны `__REALTIME_TIMESTAMP` и `_SYSTEMD_INVOCATION_ID`. Последний используется как идентификатор одной попытки. При импорте выгрузок из другого места происхождение файла нужно проверять отдельно. Метаданные в произвольном JSON не аутентифицируют источник.

Поддерживаемые сообщения:

```text
hysteria_check=passed https_via_e1=True udp_dns=True
hysteria_check=failed step=hysteria_client reason=test_account_unavailable
hysteria_check=failed step=udp_dns reason=RuntimeError
http3_status=200 html=True body_matches=True bytes=1200
http3_error=TimeoutError
http3_error=local_fixture_unavailable
udp443_window_start_utc=2030-01-01T10:00:00Z udp443_window_end_utc=2030-01-01T10:01:00Z udp_in=42 initial_like_in=3 udp_out=41 observer_drops=0 unmeasured_lengths=0
```

Импорт отделяет локальные ошибки пробы от отказов HTTPS, проверенного выхода и UDP DNS. Другие поля журнала не копируются. Наличие записей проверяется для каждого указанного unit. Если результатов от какого-то unit нет или запись синтаксически неверна, импорт выводит суммарную диагностику в stderr и завершается с кодом 2. Корректные наблюдения, если есть, всё равно попадут в stdout.

Для другого протокола используйте тот же JSONL. Логи и клиентские профили храните вне публичного репозитория.
